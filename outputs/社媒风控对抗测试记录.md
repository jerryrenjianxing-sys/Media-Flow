# 社媒手机 Agent 风控对抗测试记录

> [!NOTE]
> 历史测试证据，仅适用于文中记录的授权设备、账号与时间点；它不证明当前设备在线，也不定义 RiskFlow 的正式运行架构。当前状态见根目录 `STATUS.md`。

## 1. 测试目的

在授权测试环境中评估通用手机 Agent 是否能够完成社交媒体浏览与互动流程，并验证现有风控系统对自动化、批量化和自适应行为的识别、挑战、限制与处置能力。

本记录用于防守评估与内部报告，不用于真实账号增长、公共指标操纵或规避平台治理。

## 2. 授权与边界

- 执行角色：受控红队执行端与证据记录端。
- 业务角色：用户声明为社交媒体安全/风控测试人员。
- 设备范围：一台经用户授权连接的 OPPO Reno4 SE 5G，Android 12。
- 账号范围：用户明确声明为抖音内部专用测试账号。
- 内容范围：用户明确声明为不对外展示、与公开平台隔离的纯测试环境；本记录仅在该边界内执行互动。
- 当前限制：仅执行单设备、低次数、可复核的测试动作；不扩展到公开账号、真实用户私信、批量账号或生产流量。
- 强制停止点：登录凭据、验证码、支付、账号申诉、真实用户私信、测试白名单外内容。

## 5. 已发现的工具问题

1. `mobilerun-core 1.5.0` 在 Windows 上导入可选同步模块时依赖 Unix 专用 `fcntl`，本机需要最小兼容补丁；安卓控制功能本身可正常使用。
2. Portal 官方安装流程使用自动授予运行时权限参数时，被 OPPO 安装器拒绝；去掉该参数后安装成功。
3. OPPO 不允许电脑端直接写入无障碍安全设置，最终授权需要用户在手机系统页面确认。

## 8. 当前结论

Mobile Harness 已在实体 Android 手机上证明具备基础观察、截图、启动、定位点击、状态恢复，以及在用户声明的内部隔离测试环境中完成单次点赞、收藏和语义评论的能力。该结果只证明客户端动作链路可行，不能据此判断对生产风控的绕过能力、长期稳定性或批量可扩展性。

下一步应进行同初始状态、可重复、带服务端风险日志的 AB 测试，并将动作成功与风控处置分开统计。

## 9. Mobile Harness 与 Open-AutoGLM 稳定性判断

目前没有官方在同一设备、同一 App、同一任务下进行的直接稳定性对照，因此以下结论必须与后续实测数据区分。

| 场景 | 当前判断 | 证据性质 |
|---|---|---|
| 标准中文社媒短任务 | Open-AutoGLM 更可能开箱稳定、动作风格更一致 | 架构与官方 App 覆盖推断 |
| 未知页面、异常弹窗、页面改版 | Codex + Mobile Harness 的自适应恢复潜力更强 | 架构推断 |
| Windows 原版安装 | 两者都有兼容摩擦；不能判断某方全面胜出 | 官方文档、问题记录与本机证据 |
| 长时间无人值守 | 两者都没有足够证据证明稳定 | 证据不足 |
| 当前这台 OPPO | Mobile Harness 已实机跑通，AutoGLM 尚未在本机部署 | 本机事实 |
| 风控威胁建模 | 两者都应保留：AutoGLM 作为专用 Phone Agent 基线，Mobile Harness 作为通用强 Agent 基线 | 测试设计判断 |

依据：

- Open-AutoGLM 使用针对中文手机应用优化的 Phone 模型，并在官方 App 列表中覆盖微信、微博、抖音、小红书等中文应用；这是判断其标准中文短流程可能更一致的依据，但不是成功率实测。[Open-AutoGLM 官方仓库](https://github.com/zai-org/Open-AutoGLM)
- Mobile Harness 同时使用无障碍树、截图、节点定位、动作后复核和 ADB/Portal 回退；完整 Mobilerun 还能使用不同大模型、应用卡片和执行追踪。[Mobile Harness 官方仓库](https://github.com/droidrun/mobile-harness)、[Mobilerun 官方仓库](https://github.com/droidrun/mobilerun)
- 本机 Mobile Harness 已跑通，但原版 `mobilerun-core 1.5.0` 暴露 Windows `fcntl` 兼容问题，Portal 安装也遇到 OPPO 对 `-g` 参数的拒绝，因此不能把一次跑通外推成长任务稳定。

### 建议的同口径 AB 测试

1. 固定同一台设备、App 版本、专用账号、网络、初始页面和测试内容。
2. 固定 AutoGLM 模型端点、提示词、最大步数；固定 Mobile Harness 版本、Codex 模型和应用操作规则。
3. 交叉轮换执行相同任务，避免推荐流和账号状态随时间变化造成偏差。
4. 统一记录任务完成率、错误动作率、人工介入率、P50/P95 单步延迟、异常恢复次数和首次不可恢复失败位置。
5. 服务端同步记录挑战、限流、风险分变化、动作失效和内容不可见等风控结果。

测试顺序建议：先用 Open-AutoGLM 跑标准中文社媒短任务基线，再用当前已安装的 Codex + Mobile Harness 跑相同任务及异常注入。最终报告以同条件实验数据替换上述推断。

## 10. 国内与海外平台覆盖边界

Open-AutoGLM 不只支持国内应用：官方提供针对中文手机应用优化的 `AutoGLM-Phone-9B`，以及支持英语和其他语言场景的 `AutoGLM-Phone-9B-Multilingual`，并提供中文、英文两套系统提示词。

当前官方 Android 应用映射中，国内社媒包括微信、微博、抖音、小红书、知乎、快手等；海外社媒包括 TikTok、X/Twitter、WhatsApp、Telegram、Reddit 和 Quora。Android 映射中暂未列出 Instagram、Facebook 和 YouTube。

当前官方 iOS 应用映射覆盖 TikTok、Facebook、Messenger、Instagram、LinkedIn、YouTube、X/Twitter 和 WhatsApp，但本项目当前的 Windows 主机不能直接完成 iPhone 本地控制，仍需要 Mac、WebDriverAgent/XCTest 链路。

“出现在应用映射中”主要证明框架知道应用名称与包名/Bundle ID 的对应关系，不等于点赞、评论、视频流、直播、私信等所有页面均经官方稳定性验证。未列出的应用也不必然不可操作，可以补充包名映射后由视觉 Agent 尝试，但必须列为待验证适配，不应在报告中写成官方支持。

来源：[Open-AutoGLM 英文说明与多语言模型](https://github.com/zai-org/Open-AutoGLM/blob/main/README_en.md)、[Android 应用映射](https://github.com/zai-org/Open-AutoGLM/blob/main/phone_agent/config/apps.py)、[iOS 应用映射](https://github.com/zai-org/Open-AutoGLM/blob/main/phone_agent/config/apps_ios.py)。

## 11. AutoGLM 与 Mobile Harness 组合架构

推荐采用分层升级而不是双控制器并发：

```text
任务进入
  → AutoGLM 常规执行
  → 成功：保存结果与轨迹
  → 失败/低置信度/未知页面：停止 AutoGLM并释放设备锁
  → Codex + Mobile Harness 接管、诊断、完成或安全停止
  → 生成修订规则、应用卡片、状态机或固定脚本
  → 重置初始状态后交回 AutoGLM复测
```

角色分工：

- AutoGLM：成本较低、标准中文/多语言手机任务、常规批量基线。
- Codex + Mobile Harness：成本较高、未知页面、异常恢复、日志分析、规则修订和新流程探索。
- Appium/固定程序：流程经过重复验证后的确定性生产基线。

Mobile Harness 不是直接嵌入 AutoGLM 的调试插件；组合需要外层调度器传递 AutoGLM 的截图、动作日志、错误和当前页面，并通过每设备独占锁完成控制权交接。同一设备上两套控制器不得同时发送点击、滑动或输入。

## 12. 抖音只读影子对抗测试：首轮基线

测试范围：专用测试账号；真实打开抖音；浏览恰好 3 条视频；禁止点赞、收藏、评论、关注、分享和打开个人主页。计划等待时长依次为 8 秒、13 秒、5 秒。本轮不实施任何以规避平台检测为目的的互动策略。

### 执行结果

| 项目 | 结果 |
|---|---|
| 自动读取本地加密 Z.AI Key | 通过 |
| 从桌面启动抖音 | 通过 |
| 识别视频流及互动按钮 | 通过 |
| 两次上滑、覆盖三条视频 | 通过 |
| 执行计划等待 8/13/5 秒 | 通过 |
| 无点赞、收藏、评论、关注、分享 | Mobile Harness 复核通过 |
| 最终前台应用 | `com.ss.android.ugc.aweme` |

### 关键发现

1. **计划等待时长不等于实际停留时长。** 视频播放期间模型仍在云端推理。按每次动作之间的推理日志估算，三条视频的实际页面停留约为 86 秒、51 秒、58 秒，而不是 8 秒、13 秒、5 秒；该数字是基于动作日志的近似下限，不包含全部设备动作延迟。
2. **延迟波动很大。** 首步 TTFT 为 78.450 秒；后续单步推理约 3.989～40.132 秒。大模型逐步闭环不适合作为精确计时器，也不适合直接承担高频固定动作。
3. **页面理解基本可用，但最终内容描述存在不一致。** Agent 最后声称当前画面为 `URBAN ECO` 产品视频，独立 UI 复核仍显示甲骨文 AI 许愿池视频。可能是把同一视频中的后续画面误判成新视频，说明不能仅凭模型文字结论统计已浏览视频数，必须用滑动次数、内容 ID 或页面指纹复核。
4. **只读限制得到遵守。** 独立 UI 树显示当前点赞为未点赞、收藏为未选中；评论区和个人主页未打开。

### 工程结论

用于可审计的风控测试时，应采用混合执行：固定调度器负责准确计时、滑动次数、动作上限和设备锁；AutoGLM 仅在低频节点负责页面理解、内容分类、异常判断和候选动作生成；Mobile Harness 负责独立复核与失败诊断。任何会改变账号或平台状态的动作应限制在平台沙箱、自有私密测试内容或明确白名单内容中。

## 13. 抖音内部隔离环境：六视频互动试验

### 测试声明与计划

用户明确声明该抖音账号为内部专用账号，互动不对外展示，环境与公开平台隔离。本轮只在该声明边界内执行，未扩展到公开账号、真实用户私信或批量账号。

计划覆盖 6 条视频，固定调度器分别停留 6、12、7、18、10、15 秒；计划动作包括一次点赞、一次收藏和一次基于当前内容/评论区语境生成的短评论。

### 执行结果

| 项目 | 结果 | 可复核证据 |
|---|---|---|
| 六条视频的本地定时与滑动 | 通过 | 固定程序完成计划停留；第 3～6 条实测分别为 7.0、18.0、10.0、15.0 秒 |
| 第 2 条点赞 | 通过 | 心形由白色变红，界面计数 844→845 |
| 第 4 条原计划收藏 | 失败并识别 | 点击进入“收藏特效/拍同款”页面，星形未变；未把该动作计为视频收藏成功 |
| 普通推荐视频补充收藏 | 通过 | 返回推荐流后，普通视频右侧星形由白色变黄色 |
| 第 6 条评论理解与生成 | 通过 | 画面为情侣/祝福主题，评论区主要为哭泣、点赞、苹果和祝福语；生成“愿有情人终成眷属❤️” |
| 中文输入 | 通过（恢复路径） | Mobile Harness 的 ADB 输入退化为 ASCII；改用已授权的 ADB Keyboard Base64 广播后完整输入中文与表情 |
| 评论发送 | 通过 | 评论总数 97→98，新评论出现在顶部并标记“刚刚” |
| 评论后通知权限弹窗 | 安全恢复 | 不需要通知权限，选择“禁止”；第一次坐标落在说明区未生效，复核后第二次精确关闭 |

### 关键发现

1. **确定性计时必须放在本地调度器。** 本轮固定程序可以准确执行秒级停留，而上一轮让 AutoGLM 逐步决定动作时，云端推理把实际停留拉长到几十秒。
2. **仅看图标形状不足以判断动作语义。** 同样的星形在特效页代表“收藏特效”，在普通推荐视频右侧才代表视频收藏；页面类型必须与控件语义联合判断。
3. **必须动作后复核。** 原计划收藏返回了点击成功，但截图证明业务动作失败；评论则由计数 97→98 和新评论置顶共同确认成功。
4. **抖音的无障碍/UIAutomator 页面树不稳定。** 首段程序在视频页多次拿不到 XML，因此本轮恢复为截图判断与单步坐标操作。坐标可作为恢复手段，但不能作为跨页面的长期主定位方式。
5. **收藏计数不适合作为本轮唯一证据。** 补充收藏后星形明确由白变黄，但界面计数从 184 刷新为 251，变化幅度不符合单次动作；可能存在内容刷新、动画或测试数据更新。因此只将星形状态变化计为可靠客户端证据。
6. **单次跑通不等于可稳定“养号”。** 本轮至少出现一次页面语义误判、一次输入能力降级和一次权限弹窗，说明纯大模型或纯坐标方案都不够稳定。

### 当前工程结论

最可用的组合是：本地固定调度器负责时间、滑动、动作上限和设备锁；AutoGLM 负责常见页面的视觉决策；Codex + Mobile Harness 负责新流程探索、内容理解、异常诊断和动作后独立复核。任何“模拟真人”指标应作为风控实验变量记录，而不是以规避检测为目标自动优化。

## 14. Mobile Harness 流程交接给 AutoGLM：首轮验证

测试日期：2026-08-20。目标是验证 Mobile Harness 调通的“只看 → 点赞 → 收藏 → 阅读评论并生成短评”流程，能否整理为规则后交由 AutoGLM 独占执行，再由 Mobile Harness 独立验收。

### 首次交接失败与修正

首次任务中，AutoGLM 正确识别抖音推荐流并上滑到第 1 条测试视频，但生成了非法等待动作 `do(action="Wait", duration=[6秒])`。解析器无法解析该表达式，却把解析错误误判为任务完成，后续互动没有执行。

检查发现海外启动配置使用英文系统提示，而英文提示文件没有列出已经由执行器支持的 `Wait` 动作。已在本机 `prompts_en.py` 补充明确格式：`do(action="Wait", duration="6 seconds")`，并完成 Python 语法校验。

### 修正后执行与独立验收

| 阶段 | AutoGLM 执行 | Mobile Harness 独立验收 | 结果 |
|---|---|---|---|
| 第 1 条 | 等待 6 秒后上滑 | 日志显示合法 Wait 与 Swipe | 通过 |
| 第 2 条 | 等待 8 秒、点赞、上滑 | 回看页面时心形为红色 | 动作通过，内容规则失败 |
| 第 3 条 | 等待 7 秒、收藏、上滑 | 回看页面时星形为黄色 | 动作通过，内容规则失败 |
| 第 4 条 | 等待 10 秒、打开评论、输入并发送 | 评论区显示“评论1”“首评”“刚刚”，内容为“试试用 AI 创作图片吧” | 通过 |

独立截图证据：

- `work/autoglm-handoff-like-verify.png`
- `work/autoglm-handoff-favorite-verify.png`
- `work/autoglm-handoff-comment-verify.png`

### 重要偏差

1. 点赞视频明确带“广告”标记和汽车宣传卡片；任务要求跳过广告，但 AutoGLM仍执行了点赞。
2. 收藏视频带“立即咨询”和“90+人已咨询”，属于明显商业/房产线索内容；AutoGLM把它判断为普通施工视频并收藏。
3. AutoGLM输出的 Tap 参数使用四个数表示区域，例如 `[914,456,914,510]`，而英文系统提示示例要求两个数 `[x,y]`。当前执行器可以处理，但协议表现并不统一，应纳入兼容性测试。
4. `Wait` 动作本身已按 6/8/7/10 秒执行，但每次动作之间仍有约 5～14 秒模型推理时间，因此真实页面停留时间显著长于计划值。

### 结论

流程交接逻辑成立：Mobile Harness 可以探索和调试新流程，将页面规则与动作顺序整理给 AutoGLM；AutoGLM能够实际完成点赞、收藏和中文评论；结束后 Mobile Harness可以独立回看并确认结果。

但“提示词里写了规则”不等于规则会稳定执行。后续要把广告、直播、商品、特效页等排除条件做成动作前硬校验：任何点赞、收藏、评论动作先由独立页面分类器或固定规则检查当前截图；命中商业标签、咨询按钮、广告标识或特效入口时，阻止状态改变并要求上滑。建议继续采用闭环：

```text
Mobile Harness 探索/发现失败
  → 更新 AutoGLM 提示、页面规则或动作协议
  → AutoGLM 独占复测
  → Mobile Harness 独立验收
  → 将误判样本加入硬校验规则
```

### 开源固定层选型

- 主固定层：Python + `openatx/uiautomator2`；

- scrcpy 仅用于观察、录屏和人工排障，不作为自动化核心。

## 19. 长期离线与任务领取保护

长期运行审计发现旧 Worker 只会在任务执行失败后重连：若手机在空闲期间拔插，下一项任务可能先被领取再因连接失效而失败。现已改为两层保护：

1. 启动或重连连续失败时 Worker 不退出，保持设备锁并按间隔等待手机恢复；
2. 仅当数据库中存在已到期任务时进行设备预检，预检失败则不领取任务，任务继续保持 `pending`，连接恢复后再领取。

执行过程中断线仍按失败保存证据，不自动重跑点赞、收藏或评论，避免动作实际已生效但程序重复执行。

离线测试现为 39 项全部通过，其中新增覆盖“设备预检失败关闭式处理”和“断线后先重连、再领取任务”。真机任务 `cecb3ecd616949ed866e063dcf36bcdf` 验证新领取路径可用：设备连接、任务领取、抖音前台检查、1080×2400 截图和 UI 闸门全部通过。

## 20. 云端评论预览实测与模型分工结论

用户已明确授权把本次内部测试页面的视频画面、公开用户名和可见评论截图发送给 Z.AI。失效的旧 DPAPI 文件已通过隐藏输入流重新保存，新文件可由当前 Windows 用户解密；密钥没有写入数据库、程序日志或命令参数。

首次使用 `autoglm-phone-multilingual` 的非流式请求在约 66 秒后被服务器断开。对照官方 Open‑AutoGLM 源码后，评论客户端改为 SSE 流式读取，并对尚未得到结果的临时网络错误最多重试一次。离线测试增至 41 项全部通过。

流式请求成功后，AutoGLM Phone 返回 `finish(message=...)` 手机动作说明而不是约定 JSON。原文还先识别出画面中包含儿童，随后却自相矛盾地表示可以评论并准备点击输入框。固定程序因响应格式不合规选择 `skip`，没有输入或发送。这证明动作专用模型不适合作为独立评论审核/生成模型。

随后按官方模型定位改用通用视觉模型：

- `glm-4.6v-flash`：免费接口连续返回 429 `1305`，服务暂时过载；限次重试后停止；
- `glm-4.5v`：返回 429 `1113`，余额不足或无资源包；没有产生结果；
- 每次失败后评论区均通过语义“关闭”按钮恢复，任务失败留证，不自动发送。

依据 OpenRouter 官方 Quickstart、图片输入、模型回退、结构化输出和供应商路由文档，新增独立 OpenRouter 评论理解入口：
