## Context

参见 [proposal.md](./proposal.md) 的 Why。当前 `submit_scheduled_rounds()` 按设备和轮次直接写入 `douyin_topic_session`；Worker 在进程生命周期内持有设备锁，并按 `not_before`、创建时间和任务 ID 领取同设备任务。轮次间隔为 0 时多个任务可能具有相同 `not_before`，因此新功能不能仅靠随机任务 ID 的排序保证“第 5 轮后巡检”。

任务执行结果已经以结构化 progress 保存到 SQLite，设备批次由 `submission_id + device_id` 聚合，适合在不新增运行数据库表的情况下保存巡检分区结果。现有 `PlatformAdapter` 的 interface 面向设备初始化；把消息、点赞和访客的导航方法全部加入它会扩大所有调用者需要理解的表面。活动变更 `add-hybrid-feed-orchestration` 会同时修改提交配置和视频任务内部执行，但其阶段仍属于单个视频轮次；本变更只在完整轮次任务之间排队，二者应正交。

## Goals / Non-Goals

**Goals:**

- 在提交时生成可预测、可解释、可测试的“视频轮次组 → 巡检 → 下一组”顺序。
- 用一个小 interface 隐藏三个入口的页面导航、识别、分区失败和安全返回复杂度。
- 保持同设备唯一 Worker、现有暂停/停止/取消语义和旧任务兼容。
- 让巡检结果进入同一设备批次，但不污染视频轮次、主题与互动成功统计。

**Non-Goals:**

- 不在视频任务内部增加计时器或抢占点；这里的“5轮”是五个完整队列任务，不是五条视频。
- 不扩展现有初始化 `PlatformAdapter` interface，也不预先建立只有一个实现的跨平台 Adapter seam。
- 不通过云模型理解消息或访客内容，不做自动回复、线索评分、回赞或关注。
- 不自动修改当前运行配置、提交任务、清空未读、清理历史或执行真实设备验收。

## Decisions

### 1. 先构建纯提交计划，再原子化写入任务

新增纯函数形式的提交计划器，输入规范化配置和基准时间，输出按设备分组的有序任务定义：视频任务保持现有载荷，巡检任务携带 `submission_id`、`inspection_index`、`after_round_index`、`inspection_every_rounds` 和有限结果策略。`submit_scheduled_rounds()` 只负责把计划持久化并返回分类型数量。

计划器为同一设备的每个队列位置分配单调增加的微秒级时间偏移；用户配置的轮次分钟间隔仍决定主要时间点，偏移只解决同一时间点的稳定排序，不产生可感知等待。领取规则继续以 `not_before` 为首要顺序，因此无需新增数据库列或迁移历史任务。

例如间隔为 0、12 轮、每 5 轮巡检时，单设备计划位置依次为 1、2、3、4、5、巡检1、6、7、8、9、10、巡检2、11、12。多设备分别生成自己的单调序列，设备之间仍可并行。

备选方案：

- 运行中到点临时插入：会让长任务增加抢占、恢复和未知写入风险，且与用户选定的“排队时排好”冲突，拒绝。
- 新增数据库 `priority` 或 `queue_position`：可表达更复杂优先级，但本变更只有提交内稳定顺序，迁移成本和兼容面大于收益，暂不采用。
- 继续依赖 `created_at + id`：同一毫秒内的随机 ID 无法证明顺序，拒绝。

### 2. 巡检是独立任务类型，但与视频任务共享提交批次

增加 `douyin_engagement_inspection` 任务类型，由现有 Worker 的 `execute_task()` 分派。它不占用视频 `round_index`，而是通过独立的 `inspection_index` 与 `after_round_index` 描述位置。队列暂停会同时阻止视频与巡检领取；取消等待任务会处理两类 pending 任务；单个巡检的降级或失败不改写后续任务。

任务创建后不再根据控制台最新配置重新计算顺序。修改巡检间隔只影响下一次提交，历史和已排队批次保持原计划快照。

备选方案：把巡检伪装成 `douyin_topic_session` 的特殊 round。这样会污染轮次统计、种子和主题成功率，并让执行器承担不相干分支，拒绝。

### 3. 使用一个深模块隐藏页面复杂度

新增抖音专用 `EngagementInspector` 模块，对 Worker 只暴露一个 interface：`inspect(policy) -> EngagementInspectionResult`。构造时接收 device、recorder 和可测试的时钟/等待依赖；私信、收到的点赞、访客及安全返回是 implementation 内部步骤。结果统一包含：

- 任务级 `status`、`restored` 和副作用提示；
- 三个分区的 `status`、可证明数量、有限条目和原因；
- 本地证据索引，不包含绝对路径。

当前只有抖音一个实现，不新增通用 `EngagementInspectionAdapter`。如果未来第二个平台确实需要同一 interface，再把平台差异放到真实 Adapter seam；这符合“一种实现不制造假 seam”的模块设计原则。

现有 `DouyinAdapter` 与 `Uia2DouyinRunner` 中可复用的前台包、底部导航、返回和主信息流确认函数继续复用，但初始化用 `PlatformAdapter` interface 不增加消息专用方法。

### 4. 页面导航使用语义信号并逐分区失败

任务开始先确认抖音前台与登录状态，并在进入消息页前记录底部“消息”的未读语义。固定顺序为：

1. 进入“消息”，识别私信列表但不点击会话；
2. 进入明确的互动消息/点赞入口，只读取带“赞了你”或等价已校准语义的可见记录；
3. 返回并进入“我”，访问明确的主页访客入口；入口缺失或要求开启设置时记录 `unavailable`，不修改开关；
4. 点击语义首页或执行有界返回，确认主信息流；失败时复用现有冷启动和有界确认，仍失败则任务 `failed`。

任一分区无法可靠识别时只将该分区标为 `failed`，在页面仍可安全导航时继续其他分区。登录页、身份验证、外部应用和未知隐私页面直接停止相关路径。成功巡检不默认保存整页截图；结构化摘要限制为每分区最多 20 条、单字段长度受限。失败时只保存现有故障机制要求的最小本地截图和 UI 证据。

### 5. 配置兼容优先，调度字段不进入策略预设

新增 `engagement_inspection_enabled` 和 `inspection_every_rounds`。缺失新字段的历史配置和旧预设按“关闭巡检、默认间隔 5”规范化，避免升级后未查看方案就意外增加设备动作。控制台显式启用后保存到当前方案；套用内容策略预设不得开启、关闭或覆盖巡检调度。

提交接口返回兼容的总 `task_ids`，并增加 `video_task_count`、`inspection_task_count` 和按设备计划摘要。旧控制台忽略新字段仍可工作；新控制台根据计数显示“视频轮次”和“巡检”而不是笼统任务数。

### 6. 批次聚合保留原视频口径

控制接口按 `submission_id + device_id` 找到关联巡检任务，但现有视频 rounds 数组只包含 `douyin_topic_session`；新增 inspections 数组包含巡检条目。批次总状态仍以视频轮次为主，巡检状态独立显示，避免访客功能关闭把一个 5/5 成功的视频批次改成“部分失败”。详情按任务 ID 白名单读取结构化 progress 和受限证据。

备选方案：把巡检任务完全显示为独立设备批次。实现更简单，但用户无法看出“这是第 5 轮后的检查”，并会挤占首页最近 5 个设备批次，拒绝。

## Risks / Trade-offs

- [打开消息或访客列表可能清除未读角标] → 进入前记录可见角标，控制台持续提示该副作用；不打开具体私信会话，避免会话级已读。
- [抖音版本、账号类型和灰度页面不同] → 每个分区独立校准和状态分级；入口缺失显示不可用，不猜坐标、不修改隐私设置。
- [私信预览和访客身份属于敏感信息] → 每分区限量、字段截断、只保存在本机、不进云模型/Git/发行包；成功任务不默认保留整页截图。
- [巡检失败后下一轮仍可能遇到相同登录或页面问题] → 后续任务不被自动取消，但仍必须重新通过现有设备与页面前检；不会把巡检成功当成视频任务就绪证明。
- [活动变更同时修改提交和控制台配置] → 实施前读取 `add-hybrid-feed-orchestration` 当前状态，在纯计划器 seam 合并字段；两项测试必须同时通过，不能覆盖对方未提交参数。
- [微秒偏移改变新批次的同时间排序] → 只对同一新提交计划使用，分钟级 `not_before` 语义不变；增加零间隔、多设备和跨巡检边界的顺序测试。

## Migration Plan

1. 先增加任务类型、载荷校验、纯提交计划器和离线顺序测试；缺失字段保持巡检关闭。
2. 增加深模块与完全模拟的 UI 树测试，再接入 Worker，默认不对真实设备提交巡检。
3. 增加控制接口聚合、提交计数和控制台开关/详情，完成 OpenSpec、Python、控制台、构建、API 与浏览器分层验证。
4. 获得单独的设备预演确认后，选择一台无身份阻断的授权设备执行一次手动巡检；先确认未读角标副作用，再校准三个页面且不打开会话。
5. 单次巡检通过后，以 6 个零互动视频轮次和每 5 轮巡检建立隔离队列，验证第 5 轮后巡检、第 6 轮继续和所有写入为零。最后才允许在当前方案显式开启。

回滚时先关闭新提交入口和当前方案的巡检开关，阻止产生新巡检任务。已排队巡检不得因降级代码而变成未知任务：先等待其进入终态，或由用户使用现有“取消等待任务”显式取消，再回退 Worker 分派。控制接口保留历史 `douyin_engagement_inspection` 的只读展示兼容；SQLite、运行目录、设备档案、未读状态和应用数据均不删除、不重置。若只回滚控制台，后端继续安全读取已有新字段；若只回滚后端，新控制台必须先隐藏提交入口。

## Open Questions

- 不同账号页面对“未读数量”可能只提供红点而不提供数字；现场校准后可在不改变状态模型的前提下，将该账号记录为 `has_unread=true` 且 `unread_count=null`。
- 主页访客入口在不同版本可能位于个人页快捷入口或创作者数据页；只要两者都满足同一列表级结果与不改设置约束，可在 implementation 内选择已验证路径，不需要改变规格。
