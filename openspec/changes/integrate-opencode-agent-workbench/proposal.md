## Why

用户已选择 OpenCode 作为内嵌 Agent，希望在首页通过对话管理 MediaFlow、诊断故障、编辑流程并验证修复，而不是继续依赖外部开发会话操作复杂表单。首版采用混合界面，保留现有控制台和固定执行器，把对话、工具、记忆、修复工作区和统一发布接起来。

## What Changes

- dev.22 用户确认：默认操作模式可在聊天中直接启动冻结任务；维护、开发权限按会话显式授权并持久化。输入框高度减半。开发范围仅 MediaFlow 项目，修复通过测试后需用户在聊天中确认应用，再由独立更新流程切换本机及失败回退。本轮不打包、不推送、不更新远端；旧计划不自动执行。

- 首页增加 OpenCode 对话工作台，保留任务台、设备、记录、设置及原参数；展示追问、执行计划、确认、工具进度、停止、结果和可恢复错误。
- 将 OpenCode 作为受管 Windows 原生子服务，以本机认证接口接入，不要求用户另装 Codex、WSL 或开发环境。固定版本及依赖随程序封装，不在客户机自动升级引擎。
- 完整保留所锁定 OpenCode 版本的原有服务商目录和认证方式，仅补充独立的“千问AI平台 · Token Plan / qwen3.8-flash”，不替换普通千问按量入口、不强制用户选择某一家。
- 新增 Agent 专用模型传输适配：支持真正的工具调用和图片输入，不能复用当前拒绝 tools 并强制 JSON Object 的视觉请求配置。Agent 沿用官方 OpenCode 的原生服务商认证与本机 auth.json 存储，不增加加密适配或定制引擎；现有 MediaFlow 加密凭证保持不动，千问 Key 可由用户选择引用关联，不要求在聊天中粘贴。凭证不进入日志、源码或安装包。
- 复用现有规划、队列、维护操作和纠错证据，为 Agent 提供有结果回执的工具。参数不完整时集中追问；最终计划经用户确认后执行，刷新和重复请求不重复建任务。
- 内嵌版本化操作手册、共享流程和可查看/编辑/撤销的本机记忆。故障由 Agent 读证据、提出修改、在修复工作区编辑并测试；用户选择的“统一发布后生效”保持不变。
- 专业模式允许项目范围内高权限操作和修复，避免逐项询问无影响的读取；设备独占、未知结果不重放、破坏性操作确认和不可泄露凭证仍由程序执行，不能仅靠提示词。
- 下一未使用测试序号计划为 `0.4.1-dev.19`；实施前再次核对版本占用。保持业务队列暂停，先完成对话及无设备副作用验收，再封装和独立运行验收。

## Capabilities

### New Capabilities

- `embedded-agent-workbench`: OpenCode 会话、服务商增量配置、工具确认、运行进度、流程记忆、修复工作区及接管验收。

### Modified Capabilities

- `execution-architecture`: 明确内嵌 Agent 是业务编排与修复入口，不成为第二套设备动作执行器；修复经统一发布生效。
- `windows-distribution`: 增加原生 OpenCode 及依赖锁定、第三方声明、修复资源和独立运行验收。

## Impact

影响首页、模型设置、本地 API、后台进程管理、任务规划入口、凭证与会话存储、发布脚本及测试。新逻辑集中到 Agent 宿主、工具服务、配置适配和修复工作区模块，不把整套实现堆入 control_api.py 或复制 Worker。

已核对事实：当前唯一版本文件为 dev.18；已有 `/api/workbench/preview`、不可变提交、生命周期操作和纠错记录可复用；`model_budget.py` 的千问分支拒绝工具参数，`model_providers.py` 保留历史 10 次验收限额。已验证官方 OpenCode 1.18.29 Windows 原生启动、受管进程及一次千问真实只读状态工具调用与回传。完整原生服务商登录、安装版修复工作区及全链路断线恢复仍待验收，不以只读工具成功宣称已接管软件。

非目标：本次不重写 MuMu/业务执行器，不删除旧页面和数据，不自动恢复之前六轮任务，不更改账号，不绕过服务商限制，不上传私人模板到 GitHub，不把原始聊天或密钥作为内嵌记忆，不允许客户实例各自热改正在运行的发布程序。
