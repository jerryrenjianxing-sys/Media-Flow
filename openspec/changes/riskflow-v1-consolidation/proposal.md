## Why

RiskFlow 已经具备可运行的五设备固定执行链路，但正式架构、安全边界和后续变更规则分散在代码、旧文档与历史聊天中，且此前没有版本基线。现在需要先建立可信的项目真相和可回退的变更闭环，避免后续任务重新采用已放弃的架构或在未验收时改变设备行为。

## What Changes

- 建立 RiskFlow 唯一正式架构、安全边界、运行入口和验证顺序。
- 建立基于 OpenSpec 的 `explore → propose → apply → verify → archive` 变更流程。
- 新增项目说明、状态、运行手册、架构决定、变更记录和 Agent 工作规则。
- 将 AutoGLM、统一 Agent 池等旧材料标记为历史方案，保留证据但不再作为当前实现依据。
- 建立后续治理队列，首轮不拆分核心代码、不迁移数据库、不改变设备控制逻辑。

## Capabilities

### New Capabilities

- `project-governance`: 定义项目真相来源、变更分级、确认门槛、验证顺序、归档与回退要求。
- `runtime-safety-baseline`: 固化当前正式运行架构及设备独占、失败不自动重跑、AI 不直接控制设备、默认预览等安全约束。

### Modified Capabilities

无。当前尚未建立正式规格，本变更只新增治理和运行基线规格。

## Impact

- 新增 Git/OpenSpec 治理资产和项目文档。
- 更新旧方案文档的状态说明，但不删除历史材料。
- 不修改控制台接口、SQLite 表结构、任务状态、Worker 执行逻辑、模型请求或设备动作。
- 不创建远程仓库，不提交运行数据库、截图、日志、依赖、工具包或密钥。
