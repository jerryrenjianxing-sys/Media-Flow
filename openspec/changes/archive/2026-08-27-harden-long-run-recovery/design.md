## Context

现有固定执行器已经有主信息流外壳判断、互动严格门以及“首页—返回—关闭—应用重启”恢复链，但主题会话启动仍调用严格互动判定；信息流中的直播预览因此在第一次上滑前失败。异常阈值也把安全门拒绝与真正页面偏航混为一类。评论流程已经保存打开后的画面，但输入定位失败后的异常截图发生在评论面板关闭之后。

Mobile Harness 已在 OPPO `P7HUDEKF4XVODY4D` 上验证两轮强停冷启动：从抖音视频流和从系统设置前台两种状态都在首次有效观察时回到 `com.ss.android.ugc.aweme` 推荐流，并成功完成一次上滑。测试同时观察到冷启动期间无障碍树可能短暂为空，因此固定程序必须沿用有界轮询而不是单次读取。

## Goals / Non-Goals

**Goals:**

- 让已知可浏览但不可互动的卡片持续通过视频流，不消耗真正异常预算。
- 把现有应用重启兜底补成模式感知的恢复闭环。
- 用最少的新分支修复动态评论入口、空评论区和错误证据时序。

**Non-Goals:**

- 不让 AI、Mobile Harness 或纠错分析器进入正式设备动作平面。
- 不删除应用数据、不改变账号、不自动重放结果不明的互动动作。
- 不承诺所有未知页面都能恢复，也不取消设备级熔断。
- 不新增数据库字段、控制台参数或第三方依赖。

## Decisions

### 启动使用外壳判定，写入继续使用严格门

主题会话开始只验证可浏览主信息流外壳；循环的第一次动作仍是上滑，因此直播预览不会被互动。点赞、收藏和评论保持原严格控件与安全门，不放宽任何写入条件。

### 安全跳过与真正异常分开计数

`live`、`advertising`、`commerce`、`commercial_content` 和 `effect` 是已知阻断类别：记录原因、禁止互动并继续上滑，但不增加连续异常计数。前台包错误、无效 UI 树、无法确认信息流和恢复失败才算真正异常。保留现有可配置阈值，避免错误账号状态、登录页或设备故障形成无限循环。

### 大退复用现有恢复链，不增加第二控制器

固定执行器继续先尝试首页、返回和明确关闭，最后调用现有 `app_stop`/`app_start` 并轮询主信息流。普通模式恢复后继续；搜索模式仅在实际发生应用重启时用原查询重新进入搜索视频流。每个异常进入恢复链一次，失败即安全结束当前设备任务。

### 评论入口采用“已有选择器 + 底部语义候选”

保留当前资源号、`EditText` 和常见提示词作为快速路径；新增评论面板底部语义节点定位，点击一次后再次寻找真正可编辑控件。相比为每台手机保存评论坐标，这能覆盖动态文案并保持设备档案简洁。

### 故障证据在清理动作前保存

评论异常在关闭面板前保存截图和 UI 树，并把该路径传入异常记录。恢复后的截图可以作为补充证据，但不得替代首要故障现场。

## Risks / Trade-offs

- [直播文案变化导致未归入安全跳过] → 同时保留主信息流外壳判断和故障证据，未知信号仍进入真正异常路径。
- [重启后搜索上下文丢失] → 只有搜索模式重放只读搜索导航，不重放点赞、收藏或评论。
- [频繁重启掩盖账号或设备问题] → 保留连续真正异常熔断；重启失败立即停止当前设备任务。
- [底部语义候选误点其他按钮] → 只在已确认评论面板内、限定底部区域和评论输入语义，点击后必须出现可编辑控件才允许输入。
- [真机 UI 树短暂为空] → 使用现有约 12 秒有界轮询；超时留证失败，不无限等待。

## Migration Plan

1. 先用保存的直播预览、评论面板和空评论区证据建立离线回归测试。
2. 实施最小代码改动，运行 OpenSpec 严格校验与全部 Python 测试。
3. 使用独立验收任务、预览模式和零互动概率做单设备真机回归，验证普通模式和搜索模式恢复，不执行点赞、收藏、评论或发布。
4. 验收后重启正式 Worker 加载新代码，恢复原任务池状态；运行数据库和历史截图保持不变。
5. 回退时恢复启动判定、分类计数和评论入口改动；不删除本次验收证据，不修改历史任务终态。
