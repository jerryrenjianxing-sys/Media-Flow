## Context

见 `proposal.md`。当前 `RiskFlow.exe` 启动 PowerShell，PowerShell 再创建 Python/Node 子进程；这些进程虽然使用项目独立环境，却仍可能随 Codex 的 Windows 进程作业一起退出。RiskFlow 依赖当前用户 DPAPI 密钥、交互式桌面会话中的 ADB/USB 设备和本地浏览器，因此 Session 0 Windows Service 不是本阶段的合适宿主。

## Goals / Non-Goals

**Goals:**

- 把生命周期所有权交给 Windows 任务计划程序中的当前用户登录任务。
- 用一个轻量监督器维护现有 API、UI、分析器和设备 Worker，不改业务数据流。
- 让启动、停止、状态和异常拉起具有明确、可测试、可回退的语义。

**Non-Goals:**

- 不把 React/Python 重写成原生桌面程序。
- 不引入自动更新、代码签名或公开安装包分发。
- 不自动重试中断的设备任务，不清理运行数据库、截图或日志。
- 不让 Windows Service 在 Session 0 中直接控制手机。

## Decisions

### 1. 当前用户计划任务，而非 Windows Service

使用 Windows 任务计划程序注册“登录后运行、当前交互用户、低权限、单实例”的后台任务。它由 Windows 托管，不属于 Codex 启动链；同时继续处在能读取当前用户 DPAPI、ADB 配置和桌面浏览器的用户会话中。

备选 WinSW/原生 Windows Service 适合无交互服务器进程，但会引入 Session 0、服务账号、用户密钥和 USB 会话差异，本阶段收益不足。普通开机启动快捷方式虽然简单，但缺少任务状态、单实例和系统级重启设置。

### 2. 一个 Python 监督器复用现有 RuntimeControl

监督器只负责期望状态：周期检查 API、UI、分析器和已保存配置中的设备 Worker，并调用现有 PID、启动时间、镜像与命令标记核验后再启动。它不连接设备、不读取截图、不执行任务。

后台任务设置 `IgnoreNew`，监督器自身再使用 Windows 命名互斥体，形成双重单实例保护。心跳写入运行目录，包含宿主 PID、最近检查时间、受管角色摘要和最近错误，不包含密钥。

### 3. 复用现有停止请求表达 Worker 的期望状态

设备已有 `stop:<device>` 请求时监督器不拉起该 Worker；运行、恢复或精确重启清除该请求后才重新纳入监督。这样不增加第二套设备状态数据库。

### 4. 看门狗只恢复进程，不恢复任务

Worker 启动继续调用既有 `recover_interrupted(device_id)`。因此看门狗恢复只恢复执行能力，原运行中任务先进入失败终态，等待任务才可继续领取，符合“不自动重放状态改变动作”的已接受决定。

### 5. 启停脚本作为稳定适配层

安装脚本注册当前用户计划任务；管理脚本通过一个小型后台控制命令创建或撤销停止信号、触发任务并等待端口/心跳。`RiskFlow.exe` 继续调用现有稳定 PowerShell 入口，因此不需要在本阶段引入 Tauri/Electron。

## Risks / Trade-offs

- [用户未登录时不会运行] → 这是当前用户 DPAPI、USB 和浏览器约束下的明确边界；状态与文档中说明。
- [计划任务配置被系统或安全软件禁用] → doctor 同时检查注册状态、任务状态、心跳和端口，提供重新安装入口。
- [监督器快速重启持续失败的进程形成循环] → 固定检查间隔并对每个角色实施退避，错误写入心跳；不无限高频拉起。
- [停止信号与新任务提交竞态] → 请求整个系统停机前再次检查运行中任务；监督器仅在安全检查通过后收口进程。
- [Codex 更新时旧的直接启动进程仍存在] → RuntimeControl 的身份和幂等检查会复用真实进程；安装后进行一次受控冷启动迁移。

## Migration Plan

1. 保留并备份现有 SQLite 与运行证据，不迁移数据结构。
2. 安装当前用户后台任务但先不运行，验证注册信息和命令路径。
3. 在确认无真实运行进程后启动后台宿主；启动时既有陈旧 `running` 任务按现行规则失败收口，不自动重试。
4. 验证 API、网页、分析器、配置设备 Worker、心跳和任务计划状态。
5. 人为结束一个无状态网页进程，验证监督器只恢复该角色；不执行设备任务。
6. 回退时先确认无运行任务，再卸载后台任务并使用现有直接启动路径；数据库、证据和密钥均原地保留。
