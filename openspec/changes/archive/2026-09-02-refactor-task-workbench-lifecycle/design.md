## Context

现有 React/Vinext 页面分别读取同一份保存配置，并在首页、设备页和运行页重复推导设备数、任务数与阻塞状态。后端已有确定性的 `build_scheduled_plan` 与 SQLite WAL 队列，因此最小安全改造是在提交前增加一个深的任务规划模块，而不是改写 Worker。

## Goals / Non-Goals

**Goals:** 用一个小型接口隐藏配置规范化、设备可用性、内容版本、任务计数、耗时和写入风险判断；让任务台成为唯一提交入口；让历史任务保持可还原。

**Non-Goals:** 不实现规划中的混合视频流编排；不改变设备动作、模型主题协议、截图时机、队列领取或自动重试规则；不迁移历史任务。

## Decisions

### 1. 任务规划模块是唯一计算事实来源

新增 `run_planning.py`，外部只使用读取/保存草稿、生成预览和提交三个行为。模块内部复用现有配置规范化、内容计划解析、设备档案与调度计划构建，不把这些细节暴露给页面。

### 2. 草稿使用乐观版本并保存在现有 SQLite

新增单行 `run_drafts` 存储，记录规范化 JSON、递增 revision 和更新时间。保存携带期望 revision；不匹配返回冲突。首次读取时从既有 profile 生成 revision 1，旧 `/api/config` 写入同时更新草稿以维持兼容。

### 3. 预览哈希保护提交一致性

预览返回 `draft_revision` 与 `plan_hash`。提交必须携带二者；后端重新读取运行状态和内容计划并再次生成预览。版本或哈希变化时拒绝提交，避免设备状态或页面旧草稿造成错误任务。

### 4. 写入确认只取决于真实动作

点赞或收藏任一有效概率大于零即为写入任务；评论只有在评论概率大于零且 `preview_only=false` 时算写入。确认摘要列出可能动作但不承诺概率动作一定发生。

### 5. 兼容层不成为第二套逻辑

旧 `/api/config` 与 `/api/run` 调用同一任务规划模块；旧页面地址只做导航兼容。任务执行仍由现有固定执行器完成。

## Risks / Trade-offs

- [设备状态在预览后变化] → 提交时重新预览并用哈希拒绝陈旧计划。
- [旧客户端不携带确认字段] → 旧 `/api/run` 保持历史行为；新任务台使用严格提交接口。
- [脏工作区包含大量既有改动] → 只增量编辑规划、接口、共享外壳、五个工作区与测试，不回退其他修改。
- [自动保存请求频繁] → 页面防抖保存，后端只在内容变化时递增 revision。

## Migration Plan

SQLite 仅新增 `run_drafts` 表。首次访问从当前保存配置惰性建立草稿；回滚时旧接口和 profile 仍完整可用，新表可被旧版本忽略。
